# Report 001 — S1 verification: the harness is in place and red for the right reason

Date: 2026-09-27 · Author: verifier · Subject: `tests/s1_differential.rs` (new), work order 001

## 1. What was built

`tests/s1_differential.rs` — the differential step as designed in
`docs/verification/s1-harness-design.md`, under the two constraints the architect fixed on
2026-09-26: it fails as an **assertion**, and it drives the simulator as a **subprocess**
(`cargo run --release -- <elf> --trace`), never through a library API.

It contains 71 per-binary tests, a test-set guard, a determinism test, a differ self-check, and
six ordinary unit tests for the trusted parts (normalizer fixtures, ELF `tohost` lookup).

## 2. Measured results

| Command | Result |

| `cargo test --test s1_differential -- --ignored --test-threads=1` | **FAILED**, 2 passed, 72 failed, in 3.08 s |

The two ignored tests that pass are the guards, and they are the point:

- `test_set_is_the_expected_71` — the glob yields exactly the 71 binaries the surface is
  baselined against.
- `differ_self_check_rv64ui_p_add` — the normalizer turns `rv64ui-p-add`'s 12,064-line oracle log
  into **511 records**, ending on the halting store
  `0x0000000080000040 0xfc3f2223 p3 mem 0x0000000080001000=0x00000001`, with `tohost = 0x80001000`
  and the exit verdict 0. The differ can say yes, so a corpus of reds means something.

The 72 failures are the 71 binaries plus the determinism test, and they all say the same thing:

    rv64mi-p-breakpoint: the simulator did not produce a record stream:
      output line 1 is not a record in §4's grammar: `Hello, world!`

    pinned configuration (surface §2):
      /opt/riscv/bin/spike --isa=rv64imafdc_… --priv=msu --triggers=0 -l --log-commits \
        --log=target/s1-harness/rv64mi-p-breakpoint.log /home/aelix/tools/riscv-tests/isa/rv64mi-p-breakpoint

That is the intended red state: `src/main.rs` is still the scaffold, so the oracle runs, the
reference normalizes, and the simulator's output is rejected by the grammar check before any
comparison — with the pinned configuration attached so triage needs no re-run.

## 3. Two defects the guards caught while the harness was being written

Both were in my own glob, and both would have made the gate quietly weaker:

1. First version: 398 entries, because the filter caught source directories (`rv64mi`, `rv64ui`)
   and every other slice's binaries (`rv64ua-p-*`, `rv64ud-p-*`, `rv64uzbb-p-*`, …).
2. Second version: 142 entries, because dropping the source directories also let the `.dump`
   companions back in.

The guard is what turned both into red tests. This is the review's §3.2 addition earning its keep
before a single line of simulator code existed.

## 4. One wording gap in the baseline — now closed

§4 of the surface names traps as `illegal_instruction`, `interrupt#<code>`; Spike prints
`trap_illegal_instruction` and `interrupt #1`. §5 rule 4 lists the privilege, CSR and `mem`
rewrites but not this one, so the normalizer's mapping (`trap_foo` → `foo`, `interrupt #N` →
`interrupt#N`) was an unlisted rewrite in the harness. The architect approved the one-sentence
addition on 2026-09-27; it is baselined as **change note 2**, and §4 — the observable surface — is
unchanged.

## 5. What this does not verify

Nothing about the simulator: there is no simulator yet. The gate is red on purpose, and the next
state change is the implementer's M1, after which this report is superseded by the real corpus run.
